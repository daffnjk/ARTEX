# M2.1 — Trusted local capture and immutable observation/evaluation storage

Predecessors: M1b.1c, M1b.2b (both DONE locally, CI green).

Cognitive role: observations are the controller's feedback signal. M1a defined
the read-side contract (Observation/Resolver/EvaluationReport) but fixtures
were CLI files; M2.1 gives the harness a real trusted capture store in
PostgreSQL — append-only (immutability enforced by trigger, not convention),
host-owned writes only (models never write observations), per-task read scope
(the Resolver enforces caller/task access per the M1a contract), digest-pinned
payloads (Digest at write; kernel re-verifies at read).

## Deliverables

- schema: `harness_observations` (append-only trusted captures; PK id;
  task/experiment/context/subject/object/observed_at/complete/payload/sha256)
  and `harness_evaluations` (append-only evaluation reports, full JSONB).
  Immutability: BEFORE UPDATE OR DELETE triggers raise; no UPDATE path exists
  in code. Idempotent migration via the usual idempotent schema.sql.
- db/harness_store.go: `StoreHarnessObservation` (host API; validates harness
  limits + digest; same-id same-content insert is idempotent, same-id
  different-content is an explicit error), `Harness(taskID).Resolver()`
  satisfying harness.Resolver with per-task scope, `RecordEvaluation` append +
  `LatestEvaluations` read-back.
- cmd adapter deferred: the runner/CLI keep offline fixtures; wiring the live
  capture channel (workers writing captures through the host) belongs to the
  M2.2/M2.3 integration, not this unit.

## Acceptance

- PG tests: store→resolve→Evaluate full-stack roundtrip (M1a kernel consumes
  PG-backed observations and confirms a supported claim through the frozen
  acceptance path); tamper (UPDATE/DELETE) raises; duplicate idempotent store;
  conflicting same-id rejected; cross-task resolve misses (evidence_unavailable
  path); oversize payload rejected at store time; evaluation record append +
  read-back integrity.
- Existing suites stay green; runner extended.
