# M3.2 — Condition invalidation and planner wakeup

Predecessor: M3.1 (759516f + review fixes 39cda65).

Cognitive role: residual monitoring. When the evidence under a supported
hypothesis is retracted (finding marked false_positive, or deleted), the
hypothesis must NOT silently stay supported — it is demoted to `invalidated`
IN THE SAME TRANSACTION as the retraction, an event records the transition,
and the owning task's planner is woken to re-estimate. Re-estimation entry:
restating an invalidated hypothesis revives it to active (event-logged),
after which a new discriminating experiment can re-judge it.

## Delivered

- schema: hypotheses status gains `invalidated` (idempotent CHECK migration).
- db: InvalidateHypothesesOnNodeTx (caller's tx; only supported hypotheses
  demote — active/refuted/superseded untouched); wired into
  SetFindingStatusTx on false_positive (atomic with the status flip and its
  notification event) and into DeleteFinding (atomic with evidence removal).
  The raw SetFindingStatus setter is documented as bypassing BOTH the
  notification and the invalidation cascade (low-level path, no production
  false_positive callers).
- UpsertHypotheses: restating an invalidated statement revives it to active
  (event from=invalidated); superseded/supported/refuted still never revive
  via restatement.
- server: patchFinding (false_positive) and deleteFinding wake the owning
  task's planner (owner captured before delete); wake is best-effort like
  every existing notification path, heartbeat-bounded.
- planner render: invalidated hypotheses shown with a distinct marker and the
  revival instruction (restate to re-estimate) — the belief state the planner
  sees every round now includes what broke.

## Acceptance (verified, isolated PG)

TestConditionInvalidationLoop: false_positive invalidates the supported
hypothesis (same-tx; event from=supported) while the refuted sibling is
untouched; resolved changes nothing; restatement revives to active (event
from=invalidated); deleting the basis finding invalidates a supported
hypothesis. Matrix 28/28 PASS with race; build/vet/agent/harness green.

## Deferred

- Acceptance-version advance (v1→v2) as an invalidation trigger: completions
  already revalidate atomically (M1b.3b); invalidating hypotheses conditioned
  on old acceptance versions needs a conditioning link we deliberately did
  not add (YAGNI until a scenario demands it) — recorded.
- Retest-flow false_positive outcomes (finding_retests) route through their
  own UPDATE — hooking them needs the retest result writer; queued with the
  server-harness batch.
