# M3.1 — Conditioned claims, hypotheses and experiments in the real call chain

Predecessors: M2.3, M0.2 (DONE). This is the core cognitive milestone: the
system stops being "facts + intents only" and starts maintaining COMPETING
EXPLANATIONS with PRE-REGISTERED DISCRIMINATING EXPERIMENTS — the control-
theoretic internal model with active identification.

## Cognitive contract (what "in the actual call chain" means here)

Not type definitions: planner tools the model actually calls, worker outcome
reporting the engine actually consumes, prompt rendering the next round
actually sees, and PG state the wake-up actually re-reads. Concretely:

1. HYPOTHESES: per task, a set of competing statements about the environment
   (e.g. "the 500s come from the WAF" vs "from the app's own filter"). Each is
   a versioned row with status ∈ {active, supported, refuted, superseded}.
   Two+ active hypotheses on the same question is the NORMAL state — the
   planner is explicitly forbidden from collapsing to one narrative while
   alternatives remain untested (anti-premature-convergence).
2. EXPERIMENTS: an ExperimentSpec is declared BEFORE dispatch: action
   description + per-hypothesis expected observation ({hyp: "what we'd see if
   this one is right"}) + stop condition. It links to the intent that executes
   it. Pre-registration is structural (declared_at < dispatched_at, immutable
   expectations) — the agent cannot retrofit predictions after seeing results.
3. OUTCOMES: when the worker reports facts for an experiment's intent, the
   outcome is matched against the DECLARED expectations: an observation that
   matches exactly one hypothesis' expectation DISCRIMINATES (that hypothesis
   gains support; others are marked contradicted-pending-review). Matches
   multiple or none → inconclusive (never force-fit; M0.1 registry lesson).
4. CONDITIONING: every claim/hypothesis carries its conditions (basis fact
   ids, context version). This is the substrate M3.2 invalidates when
   conditions change.

## Data model (PG, following established patterns)

- `hypotheses`: id, exploration_id, question, statement, status, basis_node_ids
  BIGINT[], notes, created_by (planner/human), created_at, updated_at.
  Superseding/refuting is a status transition with reason, never a rewrite
  (history retained; M3.2 needs it for wakeup).
- `experiments`: id, exploration_id, question, action, expectations JSONB
  ({hyp_id → expected observation text}), hypothesis_ids BIGINT[], intent_id
  (nullable until dispatched), status ∈ {declared, dispatched, observed,
  inconclusive, invalid}, declared_at, dispatched_at, observed_at, outcome
  JSONB, basis facts. Expectations IMMUTABLE after dispatch (trigger like
  harness_acceptance).
- Claims ride on hypotheses + facts for M3.1 (a supported hypothesis under its
  conditions IS the conditioned claim); a separate claims table is not added
  until M3.2/M3.3 shows a need (YAGNI, recorded).

## Tools (real registration paths, mirroring plantodo/exploration_atomic)

- Planner: `state_hypotheses` (upsert competing set for a question; at least 2
  while any active; basis ids validated same-exploration), `declare_experiment`
  (question, action, per-hypothesis expectations ≥2, → creates experiments row
  status=declared; the NEXT add_intent for it links intent_id + flips to
  dispatched — or declare_experiment optionally dispatches via add_intent
  atomically in one tool call).
- Worker: `report_experiment_outcome` (experiment_id, observed summary,
  fact_id of the recorded observation) → engine matches against expectations
  → discriminates / inconclusive; hypothesis status transitions recorded with
  reason; M3.2 will hook wake-up on refutations (this milestone only records).
- Rendering: the planner wake-up prompt gains a hypotheses block (statements,
  statuses, open experiments) exactly like renderPlannerTodos — the model sees
  the current belief state every round.

## Acceptance sketch

- PG tests: hypothesis lifecycle transitions (no rewrite, history), experiment
  pre-registration immutability after dispatch, outcome matching (discriminate
  one-of-two; inconclusive on ambiguity/none; never auto-support without a
  declared match), basis boundary (same-exploration or direct-source).
- Tool-level unit tests mirroring plantodo_test.go (validation, persistence
  before ack).
- Baseline runner extension (optional this milestone): a live round where the
  planner states hypotheses for the seeded goal — metered, preregistration
  unchanged.
- NOT in M3.1: automatic belief revision on condition change (M3.2), candidate
  selection scoring (M3.3), clean-context reviewer (M3.4).

## Anti-goals (recorded)

- No auto-confirmation of hypotheses by the model's own narrative: status
  transitions to supported/refuted REQUIRE a discriminating experiment outcome
  (structural, not prompt discipline).
- No single-hypothesis collapse while alternatives are active and untested.
- Hypotheses are NOT evidence: they never enter prove_goal evidence paths
  (fact/finding only, unchanged).
