# ARTEX v1.2：一次授权、全量实施、完成后推送交付分支

## 0. 本指令的效力与任务性质

这是维护者发给本地编码智能体的工程执行授权与流程修订，不是 ARTEX 的运行期授权合同，不是已经完成的补丁或已通过的测试记录。

维护者要求：完成 v1.1 工程包 ENG-00 至 ENG-19 的全部约定建设内容；不再逐票征求同意；在本地实现、验证和整理交付后自动提交并推送至本项目已配置远端的专用交付分支，维护者最后统一查看。

因此，本指令明确替代此前项目执行资料中的下列流程限制：

- 每张工单完成都必须等待维护者接受后，才能开始下一张。
- 缺少同工具内的独立只读审查会话即停止工程推进。
- 本次工程禁止本地 Git commit 和专用交付分支 push。
- 只返回第一张工单的实查结果就结束整个执行请求。

只替代上述工程流程，不覆盖系统/工具权限、真实安全要求或仓库中其他仍有效的规则。不改写历史批准和测试记录，不伪造独立审查。

**允许在授权工作副本中自动实现、编写测试、必要的局部重构、相关文档/CI 修改、隔离测试数据库迁移、局部修复、checkpoint commit 和最终分支 push。**

**不授权生产数据库迁移、真实目标测试、启用未批准的凭据或付费端点、修改远端可见性、扩大权限、强推、覆盖他人改动、合入默认分支或部署生产。**

这是对工程建设的无人值守，不是对测试目标的无限授权。原方案的范围、预算、执行隔离、证据与完成门禁保持不变。

## 2. 状态与调度：验证和人工审查分开

工单开发状态：

    pending → in_progress → verified_local
                           ↘ blocked

旧的 needs_review 可以保留历史；恢复时先验证实际成果，证据满足则转换 verified_local，而不是重做整票。

review 单独记录实际事实：已有真实独立审查保留；只有实现者检查则记录 self_reviewed 或原字段兼容表示；外部审查未进行则 deferred_to_final / needs_independent_review，不填写 PASS。

新开发依赖条件：所有 depends_on 均为 verified_local 或已有合法 done_verified。

verified_local 的写入条件仍是：交付物实际存在，必测和受影响回归按原门禁通过，相关迁移/兼容检查通过，没有尚未解决的阻断缺陷，测试证据与代码对应。检查名称不能代替实际运行；missing、skip、FAIL、未知用量等不能被改写为 PASS。

`progress.json` 是工作日志，不是证据或可信批准。缺审查能力不再阻塞开发，但已知真实缺陷仍阻塞。

- start/resume：实施所选工单。

本覆盖层是新增流程记录，不整包覆盖 v1.1，不重算旧 manifest 掩盖变化。除正常追加进度、报告和真实实施产物外，保留历史。

## 3. 每票自动执行，不请求人工接力

每票自行完成：读实际代码 → 定位同义实现 → 编写有效测试 → 最小实现 → 运行验证 → 自检/可用的独立自动审查 → 修复 → 留证据 → verified_local → checkpoint commit → 下一票。

既有行为正确时，新行为测试可以直接通过，不要故意破坏代码制造红灯。出现原有测试问题应在基线复现，修复真实夹具或必要兼容问题；不能通过弱化断言换取通过。

命名、目录、类型拆分、小范围重构、必要兼容、同义接口复用等在本计划内自行决定，写 ADR，不因此询问维护者。改变安全不变量、扩大运行期范围、破坏性数据变更不属于这项自动裁量。

确有多个实现者时允许只对依赖已满足且文件不冲突的工作并行；db/schema.sql、共享类型、server/engine.go、agent/worker.go 采用单写者。没有真实多会话能力就单智能体串行，不伪造分工。

保留原每根因修复上限，失败后先进行根因复盘或回到已验证 checkpoint，再做有理由且有界的替代策略。无法解决则阻塞该票及其依赖，继续可独立完成的工单。不要因一次普通测试失败或没有审查者立即全局退出；也不要无穷循环、删除测试或将失败隐藏。

## 4. 测试和验收标准不降低

每票使用 acceptance/ENG-xx.json；整体验收使用 acceptance/all.json。原计划 84 条必测，全部必须被实际选择并通过；还应运行受影响既有回归、构建、静态检查、迁移/恢复/取消等本票约定验证。

确需移动测试包或更名，保留一一对应的旧→新映射、断言等价依据和变更记录，再运行同样严格的集合检查；不可减少必测数量、删除安全断言或规避失败。自动裁量不允许削弱标准。

各阶段不得将包级 TestMain 或 runner 的环境依赖忽略。只有专用可丢弃非生产实例已确认，才运行有写入和清理效果的 PG 测试。不得降 go.mod、不使用未知远程安装脚本、不启动生产 ARTEX 服务。

最终源码树必须再跑全体本期验收与整合回归；不能拼接二十个不同中间源码版本的绿灯充当最终通过。能安全运行的全仓回归一并运行；外部依赖缺席时记录准确范围，必需验证缺席则不能宣称全量完成。

真实模型验证仅使用此前已经配置且明确批准的端点、合成数据和已有预算。缺少条件时标 NOT_RUN 或实际阻塞，不用脚本化 Provider 冒充真实模型评测，也不自行新增付费服务。仍完成不依赖该外部条件的代码、测试与交付文档。

不要用本覆盖层的调度器单测结果充当 ARTEX 的测试结果。

这修改的是工程审查安排，不删除 ENG-15 要实现的产品 Reviewer、也不让 Worker 自己批准目标授权或正式证据。

发现授权绕过、预算旁路、证据伪造、丢失执行、跨任务读写、删除保护失效等真实阻断问题，必须修复后才能把相应任务记为 verified_local。审查是否由独立人员完成，与问题本身是否已解决是两回事。

最终的人类 code review/默认分支合并审查允许在分支已推送后进行，不再作为交付分支 push 的前置条件；已有仓库保护或强制策略不绕过。

## 6. Git：现在已授权自动 commit 与最终分支 push

### 6.1 开始时自动固定交付目标

检查工作区、现有远端、分支和已有证据，不打印带密钥的 remote URL。默认使用已经明确属于本项目的 origin；没有 origin 而只有一个明确项目远端时可用该远端。无法可靠确定目的地则记录 Git 阻塞，但继续能安全完成的本地工程，不随意新建远端、仓库或公开上传位置。

使用新的专用分支，建议 feat/artex-control-v1-1；如已存在且不是本次已有交付分支，生成唯一后缀，并记录用于后续恢复。不得直接在 main/master/默认或受保护分支推送，不强推，不改远端配置、访问权限或仓库可见性。

保留用户现有未提交改动。已有 ENG-00 六项变更经范围核对可纳入本轮；无关改动不提交、不清除、不覆盖。选择 worktree 或分支时确保已审但尚未提交的 ENG-00 文件随本轮安全保留，不用 reset --hard 或 git clean 清理工作区。

### 6.2 本地逐票提交，最终统一推送

每票通过本地验收后自动作一个可审查 commit，记录工单、测试摘要和树标识；不要每票向用户申请 commit。按明确路径暂存，先审查 staged diff，再提交。不要 blind git add .。

本地提交用于恢复，不要求维护者逐一查看。默认完成所有工单和最终验收后统一推送，不为每票主动做远端发布。

使用实际已验证的远端与分支，等价命令为：

    git push --set-upstream <已核实的远端> HEAD:refs/heads/<专用交付分支>

这不是要求使用占位符原样执行。不得 --force/--force-with-lease、不得绕过 hooks/保护规则、不得自动 merge 默认分支、打生产 release 或部署。

开始就静态检查现有 push-triggered workflow/hooks。若分支推送会触发生产部署或真实目标作业，则只允许在本次专用分支上用经过审查的最小分支过滤/新分支名避开，保持生产发布逻辑不被关闭。无法避免的既有受保护部署机制，不绕过，记录发布阻塞。

推送后在有权限工具中核对远端分支提交与本地最终提交相同。已有安全 CI 可用时读取实际结果，失败则自动修复、重验并以新 commit 正常 push；不改写已推送历史。无 CI 则标 NOT_CONFIGURED；不能读取则 NOT_OBSERVED，不能写 CI PASS。若它属于既定强制验收，则对应最终状态仍待验证。

“同步 Git 成功”只指目标交付分支已更新，不指 merge 或上线。

### 6.3 被忽略文件和日志

最终应将必要源码、测试、runner、迁移、实施规格、脱敏决策记录与最终交付说明纳入交付分支，不能只保存在被忽略的目录。

允许对经过逐项检查的确定文件作精确暂存（包括必要时精确 git add -f 指定文件），或添加仅针对这些产物的窄范围忽略例外；禁止整体取消忽略或强制提交整个 reports 目录。

提交前检查本次所有提交和最终暂存区中的密钥、DSN、凭据、真实目标证据、个人路径、数据库转储、模型上下文和大文件。发现敏感内容先处理，不能仅在最后一个 commit 删除而把密钥保留在即将 push 的历史中。

原始日志可保留在本地受限审查包；仓库中的最终报告必须有脱敏摘要、哈希、验证边界和可重复命令。不要为了满足“同步”把全部原文盲目推到远端。

全部工程结束时生成维护者从 Git 就能读到的 DELIVERY.md 与 delivery.json，建议置于 docs/control-delivery/v1_1/，实际位置在仓库中确认并纳入版本控制。

至少包含：

- ENG-00 至 ENG-19 的实现、验证和审查三维状态；功能/测试/迁移映射。
- 最终源码标识、必测 84 条的实际汇总、受影响和整合回归、build/vet/CI 结果与未执行项。
- 授权、预算、取消/恢复、证据更新、部分结案的端到端结果。
- 迁移与回退、配置和本地启动方法、默认关闭的执行通道。
- 独立审查待办、已知限制、真正未完成/受阻项目。
- 实际远端、交付分支、已推送提交、是否合并/部署（本指令默认均否）。

测试源码标识和随后仅添加交付说明的 commit 分别记录，不做“把含自身最终 commit ID 的报告提交到同一个 commit”的循环；实际 push receipt 留在最终回复或外部收据。

最终状态可以为：

- COMPLETE_SYNCED_REVIEW_PENDING：全部本期工程和必需验证完成，远端分支确认同步，人类最终 review 待进行。
- IMPLEMENTED_VALIDATION_BLOCKED：实现就绪但必需环境/验证尚缺；不能写“所有内容完成”。
- COMPLETE_LOCAL_GIT_BLOCKED：本地工程验证完成，但认证/远端/分支策略阻止同步。
- PARTIAL_BLOCKED：有真实未完成任务；写明范围、影响与已保留成果。

部署状态单列 NOT_DEPLOYED，真实模型/真实目标/有限开放批准单列实际状态。没有权限/预算不能伪装完成；“人类最终审查待办”本身不再造成工程或专用分支交付阻塞。

若确有不可解除阻塞，在不暴露敏感数据且远端允许的情况下可推送清楚标为 PARTIAL 的开发分支备份，但不能宣称全量完成。该例外不是正常提前停止的理由。

## 8. 工作持续性与反馈方式

在当前实际可执行会话中持续推进下一张符合依赖的票。不要每票询问“是否继续”，不要只输出计划、检查环境或等待审查。维护者最终统一查看，不需要重复上传每票审查包接力。

只有实际工作完成、不可绕过的硬阻塞或运行器硬限制才结束本次执行。正常进展可给很简短的不需回复的状态，不索取人工批准；最终一次给出分支、commit、验收汇总、启动方式和真实剩余项。
